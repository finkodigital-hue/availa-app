# Account deletion requests

This flow initiates a request to delete the person's Bookzenvo sign-in account, profile and associated personal data. It is separate from **Close workspace**, which retains sign-in and gives a workspace a 30-day recovery window, and from a customer's request that a salon erase a customer record. Submitting an account request does not itself delete Auth, cancel billing, remove a workspace or erase another person's business records.

`/account-data` is available without a workspace or owner role. The account menu, onboarding page, plan-blocked staff screen and native app link to it. Requests and cancellations require a provider-verified current identity and password/Google sign-in within ten minutes; enrolled two-factor authentication remains required. No new MFA enrolment is required just to request deletion. The endpoint derives the target user from the verified session, never from a submitted user/business ID.

## Ownership and service targets

**Proposed accountable owner: Jakob, or a designated Bookzenvo privacy operator. Named acceptance and the applicable retention schedule remain release checklist items.** Do not describe the operation as staffed or legally approved until the owner has accepted daily review duties, access and escalation coverage. A functioning request form is not evidence that a deletion has been completed.

Check the queue every day, including weekends or through a designated cover arrangement. Review is due 24 hours after submission. The UI describes a qualified aim to complete within 30 days; the stored `completion_target_at` is an escalation target, not an automatic purge date or a statement of legal entitlement. If legal retention, identity, third-party records or another documented issue affects completion, explain the affected information and expected timing to the requester. Obtain suitable advice where the applicable retention requirement is uncertain; do not invent a retention period.

The existing protected `/api/monitoring/client-errors` health endpoint includes aggregate overdue-review and overdue-completion signals. It returns an alert status when a requested row passes `review_due_at`, or a requested/in-review row passes `completion_target_at`. The existing hosted monitor detects that response. No account IDs, emails or request details appear in the monitor. An alert is an escalation to act, not a mechanism for deleting data. Treat an unavailable queue/migration as a monitoring fault; do not silence it by marking requests completed or shifting deadlines.

## Queue contract

- `account_deletion_requests` is private. Browser/anonymous roles have no table privileges; server RPCs are service-role-only. The authenticated server layer verifies current identity, freshness and configured MFA before requesting or cancelling. Status still requires a valid current identity.
- `requested` can be cancelled by its requester. `in_review` means an operator has started processing; further changes require contacting the operator because irreversible work may have started. `cancelled` is terminal for that request. A new deliberate request receives a new row. `completed` is an operator-recorded outcome, never set by the requester API.
- `account_deletion_request_keys` binds every request key, including aliases used while another request is active, to its original request. A delayed retry after cancellation cannot reopen a request. A cancellation specifies the expected request ID and cannot cancel a newer request. Request and cancellation transactions lock the Auth identity; cancellation also locks the selected request against an operator's claim.
- Safe status responses contain only the request reference, state, timestamps, public status message and retained-data summary. `user_id`, `contact_email` and `operator_reference` are private. Public messages must not contain internal notes, credentials or another person's information.
- `contact_email` is a request-time snapshot. Reverify the current Auth user and current verified contact before any completion notification or destructive work. Never send to a historical address merely because it is in the queue.
- `confirmation_sent_at` means **completion confirmation**, not acknowledgement. A completed row requires `review_started_at`, `completed_at`, a nonblank private `operator_reference`, and `confirmation_sent_at` on or after completion. Other states cannot claim completion confirmation.
- Queue rows deliberately have no cascading Auth foreign key: deleting an Auth identity must not silently remove the completion receipt. These records remain personal data. Apply a documented, proportionate retention/minimisation period to the request audit and its contact snapshot after completion; do not retain them indefinitely by default. Receipt keys are only useful while requests may legitimately be replayed.

## Daily review and manual completion

1. Use approved private operator access to review pending requests. Keep email addresses and account details out of public logs, monitoring and issue trackers. Confirm the exact account ID; do not match an account only by name or a reused email address.
2. Claim a requested row atomically by updating `status = 'in_review'` and `review_started_at` **where its exact ID and current `status = 'requested'` match**, returning the row ID. If no row returns, stop and reread: the requester may have cancelled, or another operator may already be handling it. Record a private operator reference. Use the existing request ID for all review evidence.
3. Reverify the live Auth identity and verified contact. Inventory owned workspaces, staff memberships, linked customer records, active subscriptions, Storage assets, messages/diagnostics and third-party processors. Distinguish data attributable to this person from other people's records and business/financial records that have a documented retention requirement. Do not assume a workspace closure flag or customer erasure routine covers the sign-in account.
4. Establish and record the deletion/retention plan before making destructive changes. Resolve subscription cancellation and any retained-workspace ownership/access arrangement. Preserve legally required financial records and reconciliation links; do not retain unrelated personal details just because a backup exists. Explain the retained categories, basis and expected duration to the requester. Update the public status message with the progress/timing they need, without internal details.
5. Execute only a separately authorised, reviewed deletion procedure. **Do not blindly delete `auth.users` or a business row:** existing foreign keys can cascade into workspace and financial records. Review those dependencies and preserve required records before removing or anonymising personal data and revoking sign-in/refresh sessions. This feature intentionally supplies no automatic Auth purge, destructive SQL script or operator button. Validate deletion in the affected stores and processors; an API return alone is not completion evidence. Backups follow their documented expiry and restore-erasure process.
6. Send a completion confirmation through the approved process to the current verified contact established before identity removal. Explain any retained categories and timing. Record real completion and confirmation times and the private evidence reference; only then mark the request `completed`. Do not fabricate a sent notification. If confirmation fails, keep the request in review and retry/escalate; never claim an email was sent.
7. After identity removal, the app's current-user verification denies old sessions. The preserved queue record is an operator receipt, not a way for a newly registered account with the same email to access the old account's status. Apply the approved retention/minimisation schedule to that receipt and processor records.

No real request, cancellation email, subscription cancellation, Auth deletion or customer-data purge is performed by the automated test suites. Browser fixtures exercise request/status/cancel and account changes with inert boundaries. Full-schema tests cover table/RPC grants, verified identities, account isolation, request-key replay, cancellation ordering and completion constraints. These checks support review; they do not constitute legal approval or App Store approval.
