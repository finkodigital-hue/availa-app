# Production operations checklist

This page separates repository automation from controls that only the account owner can enable. Never copy secrets into issues, workflow output, commits, or this document.

## Monitoring implemented in this repository

Implementation and configured schedules are not evidence of deployment, actual execution or delivered alerts. Record those separately during activation.

- **Independent monitor Worker** (`bookzenvo-monitor`) is configured to run every five minutes. It checks the production HTML shell, fingerprinted browser bundle, public `/api/health` and authenticated aggregate `/api/monitoring/client-errors`. Its public `/health` returns success only when the latest completed run is healthy and both that completion and an actual scheduled completion are no older than 12 minutes. Manual runs cannot conceal a stopped schedule. See [the monitor runbook](../monitoring/README.md) for deployment, endpoints and limits.
- **Independent external monitoring** must poll the verified monitor hostname's `/health` and `https://bookzenvo.com/api/health` every five minutes, with confirmed outage and recovery notifications to approved contacts. This is an account configuration requirement, not a repository-controlled service. Check the expected `ok` response as well as HTTP success, and reject redirects where supported. The Worker does not send alerts itself; the external service supplies notifications and covers a shared Cloudflare outage.
- **GitHub Production uptime** is supplementary, best-effort monitoring of the HTML shell, fingerprinted browser bundle, Supabase Auth and the Supabase database API. Its requested schedule is minutes 3, 18, 33 and 48 each hour; scheduled Actions can be delayed or skipped. Moving away from minute zero reduces coincident load but does not close scheduling gaps. On each push to `main`, it also waits for the exact commit marker before probing health, so an older healthy deployment cannot produce a false pass.
- **GitHub Production error alerts** is another supplementary, best-effort signal, requested at minutes 7, 22, 37 and 52. It fails when at least five uncaught browser errors arrive in a 20-minute window, a notification delivery needs manual review, an aged booking-payment issue remains open, a balance checkout or gift-card refund needs review, Stripe reports an adverse refund status, a customer-photo erasure job fails or remains pending for more than 45 minutes, the reminder job stops reporting success, or monitoring data is invalid or unavailable. Only validated aggregate counts are logged; raw responses and database errors are not printed. GitHub failure notifications also require account setup and delivery verification.
- `npm run verify:production` performs the same release smoke test on demand.
- `npm run verify:recovery-controls` prevents accidental removal of the local-only restore guardrails.

The 12-minute threshold measures the independent monitor's execution freshness. It is separate from the application's 40-minute reminder-success threshold. Five-minute schedules are intended polling intervals, not detection-time or uptime guarantees: external polling and incident-confirmation settings add delay after a stale heartbeat or failed check.

## One-time owner setup

1. Retain the existing `MONITORING_SECRET` for GitHub. It must contain at least 32 random bytes encoded as text, stored as an encrypted application Worker secret and GitHub Actions repository secret. Do not use a Supabase key for this purpose.
2. Generate a separate `MONITORING_CRON_SECRET` with at least 32 random bytes encoded as text. Store it securely in the application Worker and independent monitor Worker. The application accepts it only for its aggregate monitoring endpoint; it also protects the independent monitor's operator endpoints. Do not reuse the GitHub secret, database credentials, user sessions or reminder-send secret. Never place it in a public URL, source control or logs.
3. Follow the [monitor activation checklist](../monitoring/README.md#activation-checklist--account-operator-only): verify the account and allowances, deploy the application token support and separate monitor, record its actual hostname, and observe several real scheduled completions. Configure both external five-minute checks and verify approved alert recipients. No deployment or live drill is established by this document.
4. Prove outage and recovery notification delivery using a separate external monitor labelled `BOOKZENVO TEST ONLY` and the monitor's isolated `/drill` fixture. Do not interrupt production or replace its real checks. Record both received notifications, restore the fixture to `up`, and pause the external test monitor. A manual `/run` or healthy drill fixture does not prove scheduled execution or production health.
5. In GitHub, enable Actions failure notifications for the repository and confirm they reach at least two maintainers. Manually run **Production uptime** and **Production error alerts** after deployment; keep them as supplementary evidence.
6. In Supabase, confirm successful scheduled database backups, retention, and Point-in-Time Recovery against the RPO/RTO in `backup-and-recovery.md`. Supabase backup availability and PITR are plan/dashboard controls and cannot be safely inferred from source code.
7. Configure an encrypted, access-separated daily copy and inventory for both `business-assets` and `business-public-assets`. Supabase database backups do not include Storage objects.
8. In Cloudflare, enable Worker exception-rate and availability notifications to at least two maintainers. Keep deployment rollback available and confirm the production custom domain points at the intended Worker.
9. In GitHub, require the production build/checks on `main` before merge. In Cloudflare, verify Git deployment is connected to `main` and record the deployed commit after releases.

## Quarterly recovery evidence

Perform the disposable local restore rehearsal in `backup-and-recovery.md`. Record the selected recovery point, checksum, restore duration, core row-count checks, Storage sample checks, achieved RPO/RTO, reviewer, remediation, and next rehearsal date. Store this evidence in an access-controlled operations system, never in the repository if it contains customer or infrastructure details.

## Alert response

For an uptime failure, check Cloudflare deployment/logs and Supabase status before changing production. For an incident alert, inspect the response counts first. For browser errors, group recent `client_errors` by message and URL; for notification deliveries or payments, follow `notification-and-usage-operations.md` and reconcile provider records before any resend or refund. Avoid copying personal data into tickets. Silence an alert only after documenting its cause; do not raise the threshold merely to hide an unresolved regression.

For an independent monitor failure, inspect its authenticated `/status` using the dedicated operator credential. A stale or missing scheduled completion is itself an incident even if the website currently responds; do not repeatedly run manual probes to dismiss it. Public `/health` contains no private counts. The monitor stores fixed reason codes and bounded run history, not response bodies or customer data. Local tests and deployment dry-runs are useful checks but cannot replace hosted execution and actual alert-delivery evidence.

For `unresolvedRefunds`, compare the specific refund's current Stripe status with the charge and local booking/gift ledgers. Failed or cancelled refunds may require an accounting correction; action-required refunds need the provider's next step. A delayed notification is deliberately retained for review even if a later event succeeded. Only clear the exact review after recording the reconciliation; do not restore gift credit, change the booking ledger or issue another refund merely to dismiss the alert. Provider receipts and operator acknowledgement remain required launch evidence.

For `stalledErasureStorageJobs` or `unresolvedErasureStorageJobs`, inspect the restricted erasure job and Storage provider status. Verify the exact object paths are gone before marking a job complete; never treat the database erasure alone as proof that photos were removed. If `reminderCronStale` is true, check the scheduled invocation, its heartbeat and the provider logs before retrying anything that could send a message.
